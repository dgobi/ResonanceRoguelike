Inventory now preserves explicit instance nutrition, hydration, weight, count,
qualities/keywords, fuel, liquid, text, remains/coatings and temporary armor fields.
Factory mutable values belong to individual instances. Perk handlers and survival
configuration derive after every successful full load. Existing actor stats and
perception fields are applied on restoration. Processing in hot surface/submap
maps now advances once per actual turn and produces its result on the owning map.

unimplemented effect consumers and container/transfer boundaries. The dated route

# Content routes: status and consumer map

Purpose: find a real definition, its active consumer and a route into play before changing it. This is the first concise map, not a universal schema. Paths below are game-relative (`roguelike/`). **Active JSON** means a named consumer reads that field; it does not mean every authored field works or that its route was window-tested. The complete contract/exercise is [Crow Jerky](OWNER_LESSON.md); detailed pages for the other families are subsequent work.

`engine/data_loader.py` loads most dictionaries once at startup, recursively indexing by **JSON `id`**, not filename. Duplicate IDs overwrite in unsorted traversal. Missing/malformed files may produce empty dictionaries/warnings. Some loaders read files directly or retain module-level caches. Restart with a fresh disposable session for definition changes; existing session copies and cached maps keep their old state.

## Three different loot formats — not interchangeable

| Format / example | Actual consumer/status in this snapshot |
|---|---|
| Generic tables: `data/loot/poor_household.json`; `rolls`, `entries[].item` or nested `table`, weights | `engine/loot_table.py::LootResolver` implements this schema, but has **no external Python call sites**. Retained utility, not a demonstrated normal acquisition route. |
| Dungeon item lists: `data/loot/dungeon_weapons.json`, `dungeon_shields.json`; `rolls`, `entries[].item_id`, `nothing` sentinel | DataLoader loads them; **no active Python consumer found**. The independent review's `_populate_loot` reference is absent in this exact source. Do not teach adding an item here as sufficient for dungeon acquisition. |
| Container pools: `data/loot_pools/storage_tools.json`; `roll_count`, `items[].item_id,weight` | `engine/loot_roller.py::roll_pool` actively samples without replacement; `roll_pools` combines pools; Engine materializes containers. Extra `text_pool` metadata is ignored, so some generated notes have no text binding. |

BSP found texts use yet another *subset route*: `local_gen._place_found_texts` directly selects weighted text entries from `world_texts_*` tables and creates `lab_note` specs. It does not call LootResolver or the absent dungeon-item consumer. Preserve those distinctions when validating data.

The lab and town are also separate consumers, not interchangeable layout contracts. The old `starting_location` helper's weighted-special support does not make weighted starting_lab specials work in `main`'s active named-submap route. The Layout Painter drops unsupported metadata and exports incompatible decor characters; do not round-trip an existing layout through it as a trusted editing workflow.
