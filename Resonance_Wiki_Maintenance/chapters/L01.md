# L01 — Find, run and explain one change

Make a ration restore more hunger without changing its use behavior. This is a small definition edit with a visible state difference. It teaches where values live, how a dictionary becomes an item, and why a paid action includes more than its immediate effect.

## Starting point and prediction

Use the setup in [Start creating](#learning-path). Your independent fixture is the supplied workroom and `examples/guide1/data/items/consumables/guide1_ration.json`. It derives from `roguelike/data/items/consumables/cooked_meat.json`: the production nutrition is 220; the worked ration is 320. The fixture supplies an unmet hunger value of 0.7 solely to avoid saturation hiding the result. No campaign or production definition changes.

Before running: does 320 mean 320 percent? Does opening inventory spend time? If eating succeeds, why might the final hunger differ slightly from `0.7 - 0.32`?

## Observe the actual consumer

From the repository root:

```powershell
& $ResonancePython -X utf8 -B Resonance_Wiki_Maintenance/practice.py L01 --output evidence/guide-1/l01-worked
Get-Content evidence/guide-1/l01-worked/L01/receipt.json
```

The receipt records nutrition, before/after hunger, one paid phase, removal of the exact owned item, and an unknown-handler negative control. The actual path is `DataLoader` → `ItemFactory.create` → inventory `E` → `ItemSystem.use` → `_use_eat` → `Needs.eat`, followed by the input handler's phase charge. This run uses production input handlers in a bounded room, not natural food discovery. Its screenshot is a real renderer frame; rendering itself must leave the snapshot unchanged.

`nutrition` is definition-owned until the factory copies it into the item instance. `needs.hunger` is player-owned and normalized: 0 is full, 1 critical. With the shipped maximum 1000 and tick rate 1, the final value is `0.7 - 320/1000 + 1/1000 = 0.381`. The ordinary turn's hunger tick follows the food effect. A Python `dict` stores named values; JSON describes one, but JSON does not execute a handler.

## Vary, diagnose, make

**Guided variation:** make a lighter ration that restores 180 units and weighs 0.15. Change both fields; predict hunger 0.521 after use. Run the same command with the candidate. Weight belongs to the carried item; nutrition reaches needs only on use.

**Fault:** change `on_use` to `guide1_missing`. JSON still parses and the factory can construct it, but use reports `Unknown effect`, retains the item, and pays no phase. The standard run injects this fault only into a controlled instance and checks unchanged state. A passing syntax check is not a behavior check.

**Independent task:** make a ration for a longer expedition with a deliberate nourishment-to-weight tradeoff. Choose values below the 700-unit saturation threshold in this fixture. State the expected hunger and weight before running; explain why changing the name alone would not meet the requirement.

## Lifetimes and restart

| Context | Effect of changing the JSON |
|---|---|
| Running session | Existing catalogue and items retain their loaded/captured values |
| New instance after a new launch | Factory reads the new default |
| Loaded item | Saved instance fields may preserve old nutrition |
| Unbuilt scene | Its eventual items are constructed under the relevant scene contract |
| Generated scene | Saved physical stock persists; it is not refilled |
| New world | Can use new defaults, but needs an explicit appearance route |
