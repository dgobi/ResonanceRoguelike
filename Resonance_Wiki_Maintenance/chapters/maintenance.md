# Maintain the owner handbook

The stable reader is `Resonance_Wiki_Maintenance/Resonance_Owner_Wiki.html`. Open it directly; no server is needed. Editable chapters, examples, theme and reader stay beside the builder. This is a reviewed edition, not automatic synchronization.

## Three input scopes

`wiki-config.json` pins a full immutable `commit` and explicit `source_scope`: game, tools, authoritative docs and root guides. Both builder and validator compare those scoped checkout inputs to that revision, including added and missing paths. Text may differ only by CRLF/CR versus LF; binary bytes are exact. The manifest also records raw bytes used. A later commit containing only wiki metadata/products preserves unchanged game-source binding.

Wiki authoring inputs are hashed separately: chapters, examples, illustrations, configuration, edition evidence, theme, reader, builder, validator, shared input checker, contract tests and every root Python/JavaScript/CSS helper. The source scope covers the game, authoring tools and their project-owned dependencies consumed by edition verification. Added, changed or missing inputs invalidate stale products. HTML, manifests, build/validation reports and historical audits are excluded from their own inputs. Dependency and browser versions belong in execution receipts, rather than inventories of installations. Wiki chapters are not duplicated in the original game-document library.

Schema 3 compares text freshness by canonical SHA-256 and byte size after CRLF/CR to LF only, with exact path membership, scope and pinned revision. BOM and trailing-newline changes remain substantive. Binary files remain exact. Raw capture hashes and sizes are retained unchanged as provenance; drift checks never rewrite files. LF, CRLF and mixed-newline equivalents pass for both source and wiki authoring inputs. Rebuild after upgrading an older manifest; the checker never silently repins it.

Catalogue downloads use UTF-8, LF newlines, no BOM, and preserve whether a trailing newline exists. Each record labels the full SHA-256 and size of that exact download separately from the original raw-source capture. The static validator checks both identities; Chromium and Firefox verification performs actual downloads and hashes their returned bytes.

`source-manifest.json` records source revision, exact authoring inputs, output hashes and documentation HEAD at build time. Subsequent product-only delivery commits may differ. Current guide/source links pin the reviewed source; original historical text retains its context.

The local `.gitattributes` preserves the compiled HTML's exact generated bytes when Git checks it out, including with `core.autocrlf=true`. This policy is itself a bound authoring input. Source and chapter text still use the declared canonical freshness comparison; HTML product validation remains byte-exact. The contract test exercises all three Git newline settings and rejects a changed or missing checkout policy.

The same checkout policy preserves every `examples/guide1/` byte exactly: its patch, solution and practice receipts use raw hashes. Do not let a formatter or Git newline conversion silently change the fixed patch contract. Use the explicit reviewed regeneration route in [solutions](#practice-solutions) when changing the instructional module.

## One-time documentation setup

Use the existing game Python 3.11 interpreter selected in [L01](#L01). These commands install the pinned documentation packages into a separate directory, without changing the game's packages. Package/browser installation needs network access once; reading, building and verification then work offline.

```powershell
$DocRoot = Join-Path $env:LOCALAPPDATA 'ResonanceAuthoring/GUIDE-1'
New-Item -ItemType Directory -Force "$DocRoot/python","$DocRoot/browsers" | Out-Null
& $ResonancePython -m pip install --target "$DocRoot/python" -r Resonance_Wiki_Maintenance/requirements-docs.txt
$env:PYTHONPATH = "$DocRoot/python"
$env:PLAYWRIGHT_BROWSERS_PATH = "$DocRoot/browsers"
& $ResonancePython -m playwright install chromium firefox
```

The pinned file contains Mistune 3.4.0 and Playwright 1.56.0. `verify_reader.py` locates these directories and resolves Windows app path redirection before launching the browsers. Keep the installed packages and browser binaries together when moving the verification environment; they are not included in the handbook ZIP. The supported game dependencies/assets must already be installed, as described in L01. Native Workbench checks additionally require its built executable and npm dependencies; follow the project Workbench build instructions in the embedded source library.

## Repeatable update sequence

1. Preserve previous editions and review affected source and workflow evidence. Commit intended game and authoritative-guide inputs, preserving unrelated work.
2. Update affected chapters/examples and `edition-evidence.json`. Distinguish newly executed checks from historical evidence.
3. Deliberately set reviewed source and edition metadata. Changing a SHA alone is not review.
4. Build, validate and inspect the real reader. Repeat unchanged build/drift checks. Commit wiki delivery separately.

```powershell
$env:PYTHONPATH = "$env:LOCALAPPDATA/ResonanceAuthoring/GUIDE-1/python"
& $ResonancePython -X utf8 Resonance_Wiki_Maintenance/build_wiki.py --repo .
& $ResonancePython -X utf8 Resonance_Wiki_Maintenance/validate_wiki.py --repo . --html Resonance_Wiki_Maintenance/Resonance_Owner_Wiki.html --report evidence/wiki-integrity.json
& $ResonancePython -X utf8 Resonance_Wiki_Maintenance/build_wiki.py --repo . --check-drift
```

Install the pinned documentation-only `mistune` dependency from `requirements-docs.txt` outside the game environment. `--write-manifest` remains a compatibility spelling and cannot bypass source verification. Every successful build binds its inputs/products. A build alone does not certify browser behavior or gameplay.

A feature affecting owner workflows updates its affected authoritative guide and retains concise source-bound completion evidence. **Wiki upkeep is separately commissioned or performed manually.** Do not automatically edit these chapters, rebuild this edition or add a wiki release gate to unrelated implementation work. GUIDE-1 is an explicit handbook commission, not standing permission for later roadmap stages.

## Maintain one affected page

Suppose a later commissioned feature changes recipe processing duration. Run `check_topics.py --repo .`; inspect the reported L04/crafting pages and actual `processing_layer` consumer. Preserve the previous edition metadata under `audit/edition-<number>/`. Update the full example and its expected first paid tick, cancellation and cold-load observations; run `practice.py L04 --draft <complete-candidate> --output <new-evidence-directory>`. Keep older receipts as dated history. Update `source-map.json`, relevant chapter and edition evidence only after reviewing the new committed source. Explicitly repin `wiki-config.json` and the map together. A hash change is not prose review.

`templates/lesson.md` is a reusable small page pattern: outcome, prediction, complete edit, observation, variation, diagnosis, three hints, full answer, independent task and evidence limits. Copy it for a new lesson; for a small field correction, edit only the affected paragraph and example.

The complete serial release check is:

```powershell
& $ResonancePython -X utf8 -B Resonance_Wiki_Maintenance/practice.py all --output evidence/guide-1/final-practice
& $ResonancePython -X utf8 -B Resonance_Wiki_Maintenance/verify_edition.py --evidence evidence/guide-1/final-edition
& $ResonancePython -B Resonance_Wiki_Maintenance/package_guide.py --output evidence/my-wiki-release.zip
```

The GUIDE-1 packager reads those named final-proof directories plus `evidence/guide-1/workbench/index.json`. Preserve the previous archive/receipts before replacing them. It refuses changed example hashes, a different reviewed source, failed lessons or browser evidence for different HTML bytes. The native index records the actual executed authoring, typography and captured-room commands; rerun affected native workflows and refresh their evidence when their source changes. Reusing a dated receipt is appropriate only while its recorded implementation and scope still match. This packaging step verifies evidence identity, not the truth of newly written prose.

Reading requires only a browser. Rebuilding needs the pinned `mistune` from `requirements-docs.txt`. Browser verification additionally uses Playwright 1.56.0 with its Chromium/Firefox binaries under `%LOCALAPPDATA%/ResonanceAuthoring/GUIDE-1/`; install these documentation dependencies outside the game interpreter's package directory. The exact environment and commands are recorded by the edition gate. The game lesson checks require the Windows/Python 3.11 runtime and checkout assets; the ZIP does not redistribute those dependencies. Keep your plain-text notes/drafts outside disposable roots and copy them with any moved bundle. No browser-only course progress is stored.

After a manual or commissioned update, inspect `git diff`, stage only intended files, commit accepted work and publish only when authorized. Compare the pushed branch revision with `git ls-remote origin refs/heads/main`. Do not include unrelated drafts or personal saves. Source remains separately pinned if the new commits contain only handbook content/products.
