# L14 — Diagnose and maintain independently

Repair an unfamiliar symptom by finding the first broken relationship, then leave a useful explanation and focused evidence. The goal is neither guessing edits until something happens nor asking an LLM to recreate the feature.

## Starting fixture and prediction

Use the independent ration/room fixture. Its worked diagnosis includes a capability string that parses and constructs but has no handler. Predict what each check can establish before running it:

```powershell
& $ResonancePython -X utf8 -B Resonance_Wiki_Maintenance/practice.py L14 --output evidence/guide-1/l14
```

The normal action succeeds; the deliberate unknown-handler action leaves time/resources unchanged and emits a diagnostic. The input driver records the distinction. That is a narrower, more useful conclusion than “items verified.”

## Work a diagnostic ladder

1. **State the mismatch.** “I expected one consumed ration and one phase; it remained and the turn did not change.” Include source revision, exact candidate, initial ownership and input.
2. **Check syntax without overclaiming.** `python -m json.tool candidate.json` proves parseability, not supported semantics or enrollment.
3. **Locate the loaded definition.** Check the scanned directory, exact ID and actual process/capture. A stale catalogue or same-ID saved instance can explain old values.
4. **Find construction and activation.** Follow factory fields, then the actual input/capability/registration. A valid helper with no caller is not reachable behavior.
5. **Observe before mutation.** Record exact object, resource and turn deltas. Use a breakpoint in the owning method or a temporary local log, then remove diagnostic changes from the final patch.
6. **Distinguish lifetimes.** New default, loaded object, pending room, generated scene and new-world selection need different checks.
7. **Repair the owner and regress the symptom.** Fix the capability string or implement the missing handler; do not charge time to hide a rejected action. Repeat the smallest check that would fail under the original defect.

For a Python traceback, start at the final exception message and the nearest relevant project frame. Read the value/contract there, then follow callers upward only as needed. `rg -n` finds symbols; an editor breakpoint lets you inspect state without inventing a second consumer. Avoid dumping entire personal saves or secrets into evidence.

## Guided variation and realistic faults

Add an unknown field such as `healing_bonus` to a complete ration candidate while preserving `on_use:eat`. It can be retained/parsed while `_use_eat` never reads it. The correct diagnosis is a missing consumer, not a broken JSON parser. The guided solution removes that inert field or commissions a real new primitive using L10's complete path; do not claim it heals.

Other useful diagnosis targets are a room tested against an old capture, a new item with no pool/container binding, shared action cooldown ID, a boolean accepted as a saved counter, or a timer advanced by rendering. Pick one; create a safe failing control in the same fixture and show an observation that rules out another likely cause.

**Independent task:** diagnose a different fault without reading its solution first, propose the smallest repair, run the relevant input/state check, and update one affected reference paragraph with source and evidence. Acceptance: a precise symptom, competing hypotheses, a distinguishing observation, scoped diff, meaningful regression and honest limits. Reference lookup is permitted; automatic learning certification is not.

## Keep and explain the change

Read [Maintenance](#maintenance) for exact main/checkpoint/scoped-commit and handbook build steps. Before substantial changes preserve committed state with a named tag and preserve any uncommitted affected bytes separately. Review `git diff -- specific/path`; stage only accepted paths. To discard practice, restore only the known change or use the patch guard's conflict-checked recovery. Never blanket reset or clean to simplify a diff.

Update the affected authoritative guide when implementing a feature. Whole-handbook upkeep remains a separately commissioned/manual action. When you deliberately update it, use the page template, topic map and drift report; review the prose, rerun the changed example, rebuild and inspect. A new SHA is not a prose review.
